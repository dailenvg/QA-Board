# Squint (pinpoint demo)

Next.js 15 app with two jobs:

- **Squint**, a visual review tool. Paste a website address, or upload images or a PDF, to create a project inside a folder, then switch to Comment mode and click or tap to pin numbered comments. Comments can be edited, resolved, reopened and deleted, and the panel splits them into Active and Resolved. Each project shows a status: _Ready to review_, _Comments in_ or _Comments resolved_. On a website, comments pin to a full-page snapshot. Comments export as a ZIP, Markdown or JSON written for AI coding agents, and a single project can be shared with clients by link. There is no account. The workspace lives in this browser (data in `localStorage`, images in IndexedDB), and a project is only stored on the server when you share it with clients.
- **The pinpoint host**. It wires `@pinpoint/widget` and `@pinpoint/server` together, so preview deployments get the review widget on every page.

```sh
cp .env.example .env.local   # set PINPOINT_REVIEW_TOKEN and NEXT_PUBLIC_PINPOINT_ENABLED=1
pnpm --filter @pinpoint/demo dev
```

Squint runs without environment variables. Sharing and snapshots have optional ones, listed under [Environment](#environment). The other `.env.local` values are for the widget.

## Routes

| Route                   | What it is                                                                                                                                     |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `/`                     | Overview: every top-level folder as a glass folder card holding its newest projects (subfolders' included). Old `?folder=<id>` links redirect. |
| `/f/[id]`               | Folder: breadcrumb, subfolders, status filter and project cards. Unknown ids get a way back to the Overview.                                   |
| `/p/[id]`               | Viewer: Browse or Comment mode (shortcut `C`), pins on the canvas, comments panel. `?page=<n>` opens a page.                                   |
| `/s/[token]`            | Shared review link for clients: view and add comments. No workspace links; `noindex`, no referrer.                                             |
| `/api/shares`           | Owner share API (owner key in `x-squint-owner-key`): create, push, pull, images, revoke.                                                       |
| `/api/s/[token]`        | Client share API: read, images, add a comment, share-scoped capture.                                                                           |
| `/sandbox`              | Static sample page to review in Squint. The widget e2e specs also run on it.                                                                   |
| `/api/frame-check?url=` | Reports whether a URL may be shown in an iframe here.                                                                                          |
| `/api/capture`          | `POST { url, width }`: full-page JPEG snapshot of a public website (page size in `x-capture-*` headers).                                       |
| `/review-link`          | Shareable widget link on previews (or locally with `PINPOINT_ENABLE_REVIEW_LINK=1`).                                                           |
| `/api/pinpoint`         | pinpoint widget API.                                                                                                                           |

Open `http://localhost:3000/sandbox?review=<token>` to try the widget.

## How Squint works

- **Storage.** Projects, folders and comments live under one versioned key, `squint:v3`, read through a `useSyncExternalStore` store (`lib/store`). Other tabs stay in sync through the `storage` event. If the browser blocks storage, Squint still works but nothing survives a reload. Unreadable data shows a recovery screen with a backup download instead of crashing. Writes that hit the storage quota are rejected and reported. Uploads (PNG, JPG, WebP or GIF, up to 15 MB) are downscaled to a 2400px longest edge and re-encoded as WebP or JPEG before they are saved. Images (uploads, snapshots, comment crops) live in IndexedDB. Data saved by earlier builds is migrated on load, all or nothing. Under `squint:v1` the images were inline, so they move to IndexedDB first. From `squint:v2`, each image project becomes a project with one page (`page-1`) that keeps pointing at its image (`image:<projectId>`), nothing is copied, its comments that aren't on a snapshot move onto that page, and every folder sits at the top level. The data is then saved as `squint:v3` and the older keys are removed. If an image can't be stored or `squint:v3` can't be written, the older key is left exactly as it was, the visit runs unsaved, and the next load tries again. Builds from before a migration can't read the newer key. The theme has its own key, `squint:theme`.
- **Pages.** In the New project dialog, Image takes one or more files (up to 50). With several, choose **One project per file** or **Combine into one project**; combined pages can be reordered by dragging their handles, or by focusing a handle and pressing the up and down arrow keys, and any file can be removed first. Each file is prepared on its own, with its progress or error shown. A project with several pages shows **Page n of N** with previous and next, and a thumbnail strip with each page's open comments. `[` and `]` change pages directly. PageDown and PageUp read on like a PDF reader: they scroll the canvas by about a screen first, and change pages only once it's at the bottom (or the top). None of these keys work while typing. The address keeps `?page=<n>`, so links open the same page, shared links too. The comments panel shows **All pages** (the default; each card says its page, and selecting it shows that page) or **This page**. An image project holds its pages in reading order (`source.kind` is `pages`). Each page has its own picture and size, and every comment that isn't on a snapshot names its page (`pageId`). Page ids are unique within their project only.
- **PDFs.** PDF mode takes one PDF up to 50 MB. Its first kilobyte must hold a PDF header (`%PDF-`) before pdf.js sees it. pdf.js (`pdfjs-dist`, loaded only when a PDF is chosen) renders the pages one at a time in a worker bundled with the app (no CDN), each to a picture at most 2400 px on its longest edge, stored like an uploaded image. Progress shows as "Rendering page 4 of 18", and **Stop rendering** stops it and ends the worker. A PDF with more than 50 pages offers **Use the first 50 pages** or **Choose another PDF**. A password-protected, damaged or empty PDF, or a page that fails to render, adds nothing and says why. pdf.js runs locked down: no XFA, and nothing fetched from anywhere but the app. Its standard fonts, CMaps, ICC profiles and WebAssembly image decoders (JPEG 2000, JBIG2, color management) are copied from `pdfjs-dist` into `public/pdfjs/<version>/` before `dev` and `build` (`scripts/copy-pdfjs-assets.mjs`; git-ignored, about 2.5 MB in 196 files, never its scripting sandbox) and served same-origin. Pages are painted to a canvas, so nothing in them is a link or a form (see [Known limits](#known-limits) for what else a rendered page loses). Unless you give it a name, the project is named after the file, and its pages are "Page 1", "Page 2" and so on.
- **Folders.** Folders nest to any depth. **New folder** in the sidebar makes a top-level folder, and **New folder inside** (in a folder's menu on its page, on its card and in the sidebar) makes one inside it. A folder's page shows where it sits (Overview › … › folder; deep paths fold their middle behind "…"), then its subfolders as folder cards, then its projects. A folder's count includes every project inside it at any depth; a folder with subfolders says so ("5 projects in all" on its card and in the sidebar). The sidebar shows the folders as a tree (`role="tree"`) with one Tab stop: the up and down arrow keys, Home and End move through it, right and left open and close a folder (or go to its first subfolder or its parent), and Enter opens its page. Shift+F10, or the context-menu key, opens the focused folder's menu, and Escape brings focus back to the folder. Open folders are remembered in this browser (`squint:folder-tree`), and the open folder's parents open to show it. **Move folder** (in each folder's menu) picks a new place in the folder tree, or the top level; a folder can't go inside itself or its own subfolders (those choices are shown, disabled, with the reason), and **Move project** picks from the same tree. Each folder records its parent (`parentId`, `null` at the top level). On load, a folder whose parent is missing moves to the top level, and folder cycles are broken.
- **Overview.** `/` and `/f/[id]` share one layout, so the sidebar stays put and its active indicator glides between Overview and folders. Each folder card is one link to its folder page: click or tap the glass, the artwork or the Squiggy key. Hovering a folder, or tabbing into it, fans out its four newest projects, and each one links to the viewer. The `···` chip in the card's top-right corner makes a new folder inside it, renames it, moves it or deletes it. A project created on the Overview drops into its folder and you stay put; the toast offers **Open**. Each folder gets one Native Pet product color from its place in the grid (`lib/brand-palette.ts`), shared by its generated artwork and its mascot, so no two folders in a row or column match. A folder's color can change when the column count changes or folders are added or removed; its art style and arrangement come from its id and stay the same.
- **Search.** The search field on the Overview and folder pages (top right on wide screens, in the sidebar's header on narrower ones) finds any project or folder by part of its name, in any folder at any depth, ignoring case and accents (`lib/store/search.ts`). Results are grouped into Folders and Projects (names that start with the query first, then A to Z; up to 5 folders and 8 projects, with a count of the rest), and each shows where it sits ("Client work › Q4"). The up and down arrow keys move through them, Enter opens one, ⌘Enter (Ctrl+Enter) opens it in a new tab, and Escape clears the field, then leaves it. `/` or ⌘K (Ctrl+K) focuses it from the Overview or any folder page, except while typing or with a dialog open. On phones it's an icon button that opens the field across the header.
- **Undo.** Deleting a project or a comment, and resolving a comment, shows a toast with **Undo**. Deleting a folder deletes everything inside it, subfolders included, and can't be undone. Its confirm counts the subfolders, projects, comments and share links that go with it. When any comments or share links would go, the folder's name has to be typed first ("Type Alpha to confirm"), and **Delete folder** or Enter before it matches explains what's missing instead of deleting. Otherwise Cancel is focused first. If the deleted folder's page, or a subfolder's, is open, Squint goes back to the Overview.
- **Status.** Derived, never stored: no comments is _Ready to review_, any active comment is _Comments in_, and all comments resolved is _Comments resolved_.
- **Frame check.** Before a website loads, `/api/frame-check` fetches it server-side (HEAD, then GET when needed; 6s timeout; up to 4 redirects) and reads `X-Frame-Options` and CSP `frame-ancestors`. Only `http` and `https` are fetched. Every hop is resolved first, and the server won't fetch an address that points at a loopback, private, link-local or otherwise non-public network.
- **Screenshot fallback.** Sites that refuse framing, can't be reached, or don't load within 15 seconds get a fallback with **Upload a screenshot instead** (the project becomes an image and keeps the original URL) and **Open site in new tab**. When the server can't tell (for example a local address), the browser simply tries.
- **Snapshots.** On a website project, Browse shows the live iframe and Comment mode shows a full-page snapshot, taken server-side at the stage's width (`lib/capture`). Pins are placed on the snapshot, so they scroll with its content. **Refresh snapshot** takes a new one, and earlier comments stay on the snapshot they were placed on: their card says _Earlier snapshot_, and selecting one switches the stage to it. If the first capture fails, the stage says why and offers **Retry**; owners can also upload a screenshot instead. Snapshot and screenshot images live in IndexedDB (`lib/blob-store`), their metadata in `squint:v3`. Once nothing uses an image, it's deleted about a minute later, and never while Undo could still bring it back.
- **Capture safety.** `/api/capture` accepts only `http` and `https` addresses and checks the address the same way the frame check does. Every connection the headless page makes, redirects and subresources included, goes through a per-capture proxy that refuses non-public addresses when it connects. Limits: width 320 to 2560 px, height 16,000 px (taller pages are cut off), image 4 MB (a bigger page is rendered at a smaller scale, which is recorded on the snapshot), 25 seconds per capture, two captures at a time per server instance (on Vercel the second waits for the first), and ten requests per minute per IP. Locally it uses the Playwright Chromium from `pnpm exec playwright install chromium`; on Vercel, `@sparticuz/chromium-min`, which downloads the Chromium pack for the function's architecture on first use and keeps it in `/tmp`. With `SQUINT_CAPTURE_URL` set, captures go to an external service with the same contract instead (see [Environment](#environment)).
- **Comment screenshots.** Posting a comment saves a PNG of the part of the snapshot or image that was on screen, with the pin marked. It shows on the comment card and opens larger.
- **Export.** The viewer's **Export** menu downloads a ZIP, or the Markdown or JSON on its own (`lib/export`). The ZIP holds `comments.md`, `comments.json` and `screenshots/<NN>-<id>.png` (`<NN>-p<PP>-<id>.png` for a pin on page `<PP>`), plus a page project's page images in `pages/<PP>.<ext>` and the full-page snapshots the comments sit on in `snapshots/`. Images are capped at 40 MB in total: pages with comments first, then the other pages, then snapshots; the rest are listed as left out. The Markdown is written for AI coding agents: a short header on how to use it (with a page project's pages listed), then one section per comment, active ones first, each saying which page it's on and where in page px. The JSON follows the versioned schema `squint.comments/2`; what changed from `squint.comments/1` is noted in `lib/export/json.ts`. Files are named `<project-slug>-comments-<yyyy-mm-dd>.<ext>`. Export is disabled, with the reason shown, until the project has a comment.
- **Sharing.** **Share** in the viewer creates a share link (`/s/<token>`) to one project and uploads a copy of it to the server. The owner's workspace stays in their browser.
  - **Clients** see every pin and comment, can browse, take snapshots of the project's own address (never an address they choose), and add comments with screenshots. They can't resolve, edit, delete or move anything. They can export what they see (ZIP, Markdown, JSON). The page has no links into a workspace, is `noindex`, and sends no referrer.
  - **Sync.** The owner's viewer pushes every change to the server and pulls client comments on open, every 15 seconds while the tab is visible, and on focus. The owner's copy wins. The client's view refreshes on the same schedule.
  - **Revoke.** **Revoke link** deletes the server copy, and the link answers 404. Sharing again creates a new link. Deleting a shared project, or a folder holding shared projects, revokes its link once the delete is final (when Undo is no longer offered). A revoke that fails is kept in `squint:v3` and retried until the server confirms it.
  - **Pages.** A page project's pages travel with it, each picture under its own key (`page:<pageId>`, then `page:<pageId>:<rev>` once its picture is replaced, so a replaced page is uploaded again). A client's comment names the page it's on, and the server refuses a page the project doesn't have. Before anything is uploaded, the share dialog checks the project's images against the limits below and says when the project is too big to share. Shares created before pages are converted by migration `006_squint_share_pages`, with the same page id the owner's browser gives the project, so nothing is sent again.
  - **Unsent comments.** A comment that fails to post keeps the composer open with its text, an inline error and **Retry**, and its pin is marked unsent. Sending again reuses the comment's id, so it can't post twice.
  - **Security.** The share token and the owner key are 32 random bytes each; the server stores only their SHA-256 hashes and compares them in constant time. The owner key travels in `x-squint-owner-key`. The server enforces who can do what; the UI only reflects it. Client writes are rate limited per IP: 20 comments and 6 captures a minute.
  - **Storage.** Shares live in Postgres when `DATABASE_URL` is set. Otherwise they live in the server's memory, one copy per instance, lost on restart: that is for local use only. Images go to Vercel Blob (private) when `BLOB_READ_WRITE_TOKEN` is set, otherwise into the share store, and are only served through token-gated routes (`lib/share`, `lib/share-client`). No request or response carries more than 4 MB of image, since Vercel Functions stop at 4.5 MB: bigger images upload in parts and download in byte ranges.
- **Pin anchoring.** Pins are stored as percentages of their surface: a snapshot, or a page. Website comments from before snapshots are anchored to the visible frame instead, shown only in Browse mode and labelled _Live page_.

## Squiggy

Squiggy is Squint's mascot. Its accessible name is "Squiggy, " plus the mood's label from `moods.ts`, such as "Squiggy, thinking"; Idle reads "relaxed" and Resolved reads "celebrating". The mascot component is `Squiggy` (`components/brand/mascot/Squiggy.tsx`).

The Squiggy at the top of the Overview reacts to the workspace (`lib/squiggy`). Its mood comes from four layers, highest first (a reaction lasts 2.4 seconds):

| Layer     | When                                                                       | Mood                           |
| --------- | -------------------------------------------------------------------------- | ------------------------------ |
| Reaction  | A comment is resolved                                                      | Resolved                       |
|           | A project is created                                                       | Happy                          |
|           | A project, folder or comment is deleted, or a change can't be saved        | Surprised                      |
| Attention | Squiggy is poked (for 1.6 seconds)                                         | Happy, with a wink             |
|           | A New project button is hovered or keyboard-focused, or its dialog is open | Listening                      |
| Asleep    | No pointer, keyboard, touch or wheel input for 60 seconds                  | Sleeping, until the next input |
| Ambient   | No projects (until the first input of the visit)                           | Sleeping, then Idle            |
|           | 10 or more active comments                                                 | Surprised                      |
|           | Any active comments                                                        | Thinking                       |
|           | Every comment resolved                                                     | Happy                          |
|           | Only projects without comments                                             | Idle                           |

The latest reaction replaces the one showing; there is no queue. Undo never triggers one. Listening starts once a New project control has held attention for 150 ms and lasts 400 ms after it lets go, so a passing pointer doesn't count and moving between controls doesn't flicker. An ambient mood stays at least 1.5 seconds before the next replaces it. The thresholds and timings are constants in `lib/squiggy/mood-engine.ts`. The store's actions (`lib/store/actions.ts`) emit the events (`lib/squiggy/events.ts`), so every way of resolving, creating or deleting is covered.

When Squiggy has something specific to say, its line replaces the hero's subline: "3 comments waiting in Client work" (a link to the folder with the most active comments directly inside it), with "(12 across all folders)" added when other folders have active comments too, or "All caught up. Every comment is resolved." With no projects, or only projects without comments, the usual subline shows. During a reaction, the bubble shows a line for the event instead, never a link: "One down. Nice." (resolved), "Homepage is in and ready to review." (created; a name over 32 characters is cut after its last whole word that fits, with "…"), "Gone. You can still undo it." (a project or comment deleted, while its toast offers **Undo**; a deleted folder, which has no Undo, gets "Gone. That one can't be undone."), or "That didn't save. Your browser storage may be full." It lasts only what's left of the reaction's 2.4 seconds, also when Squiggy appears after the event (a resolve, then straight back to the Overview), and then the bubble goes back to the workspace line or the subline. The bubble never changes the hero's height: an invisible copy of the usual subline sizes it. Every line is plain text, not announced; the toasts already announce each event. With reduced motion, the moods still change, as still poses.

Every other Squiggy (the comment panel's tabs, folder keys, empty states and error pages) keeps its own fixed or contextual mood.

## Environment

Squint reads four optional variables. Copy `.env.example` to `.env.local` to set them locally.

| Variable                   | When set                                                                                               | When unset                                                                         |
| -------------------------- | ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| `DATABASE_URL`             | Shares are stored in Postgres (tables `squint_*`, migrated on first use).                              | Shares live in the server's memory, per instance, lost on restart. Local use only. |
| `BLOB_READ_WRITE_TOKEN`    | Shared images go to Vercel Blob as private blobs.                                                      | Shared images are stored with the share's data.                                    |
| `SQUINT_CAPTURE_URL`       | Captures go to this external service (same contract as `POST /api/capture`).                           | Captures run on this server in headless Chromium.                                  |
| `SQUINT_CHROMIUM_PACK_URL` | On Vercel, Chromium's pack tar is downloaded from this https URL, such as a mirror near the functions. | The pack comes from the matching Sparticuz/chromium GitHub release.                |

Blob URLs never reach a browser: images are served through token-gated routes either way. `DATABASE_URL` is shared with the pinpoint server, which uses it for its own storage when the GitHub variables aren't set. With `SQUINT_CAPTURE_URL`, Squint still checks the top-level address, but the external service has to refuse private addresses for redirects and subresources itself.

## Known limits

- **Signed-out captures.** Snapshots are taken server-side, so pages behind a login are captured signed out, and personalized or location-dependent content may differ from what a reviewer sees.
- **Snapshot size.** Captures are scaled down as needed to stay under 4 MB, so a long or detailed page can come out at a lower resolution. Pages taller than 16,000 px are cut off.
- **Per-instance limits.** Rate limits and the two-captures-at-a-time cap are kept in memory, so they apply per server instance, not across a deployment.
- **Untested backends.** Postgres storage has only been tested on PGlite (Postgres compiled to WebAssembly, used in the unit tests), not on a hosted Postgres server. Vercel Blob storage hasn't been tested against a live store.
- **Public capture endpoint.** `/api/capture` is public: anyone can ask it for a snapshot of a public site. It is guarded by the address checks and rate limits above, not by authentication.
- **Cold starts.** On Vercel, the first capture on a new instance is slower while Chromium starts.
- **Share size.** A share holds up to 40 MB of images: 2 MB per comment screenshot, 8 MB per snapshot and 15 MB per page. A project's pages are stored to fit in 32 MB of that, so any project of up to 50 pages can be shared with room for snapshots and screenshots: each page gets up to 1.2 MB, and in a project of more than 27 pages an even share of 32 MB (about 670 KB at 50 pages). Combined images over their share are re-encoded when the project is made, and PDF pages are rendered to fit. If snapshots and screenshots take a project over 40 MB, the share dialog says so before anything is uploaded.
- **PDF fidelity.** Each PDF page becomes a flat picture, at most 2400 px on its longest edge and re-encoded as WebP or JPEG at 1.2 MB or less (less in PDFs of more than 27 pages; see Share size). A page that doesn't fit at full size is drawn smaller, down to 1000 px on its longest edge, so very fine print can come out soft, and a page too detailed to fit even then stops the import ("Page 4 of that PDF is too detailed to store"). Text can't be selected or searched, and links, form fields, media and scripts don't work. XFA forms aren't rendered, so such a PDF shows only its regular page content, which for some forms is just a placeholder.

## Tests

`pnpm test:e2e` from the repository root (run `pnpm exec playwright install chromium` here first). The suite builds into `.next-e2e` and runs on desktop Chrome and a Pixel 7 profile. Squint specs mock `/api/frame-check` and `/api/capture`, so they never touch the network. `pnpm test` runs the unit tests (Vitest).
