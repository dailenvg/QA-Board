# Squint (pinpoint demo)

Next.js 15 app with two jobs:

- **Squint**, a visual review tool. Paste a website address, or upload images or a PDF, to create a project inside a folder, then switch to Comment mode and click or tap to pin numbered comments. Comments can be edited, resolved, reopened and deleted, and the panel splits them into Active and Resolved. Each project shows a status: _Ready to review_, _Comments in_ or _Comments resolved_. On a website, comments pin to a full-page snapshot. Comments export as a ZIP, Markdown or JSON written for AI coding agents, and a single project can be shared with clients by link. The dashboard and viewer need an account ([Accounts](#accounts)); clients open shared links without one. The workspace lives on the server (Postgres, files in Vercel Blob), so any browser signed in to it sees the same folders, projects and comments.
- **The pinpoint host**. It wires `@pinpoint/widget` and `@pinpoint/server` together, so preview deployments get the review widget on every page.

```sh
cp .env.example .env.local   # set PINPOINT_REVIEW_TOKEN, NEXT_PUBLIC_PINPOINT_ENABLED=1 and DATABASE_URL
DATABASE_URL=postgres://… ADMIN_EMAIL=… ADMIN_PASSWORD=… COMPANY_SLUG=… COMPANY_NAME=… \
  COMPANY_EMAIL=… COMPANY_PASSWORD=… pnpm --filter @pinpoint/demo seed:accounts
pnpm --filter @pinpoint/demo dev
```

Signing in needs `DATABASE_URL` (any Postgres; a local one in Docker works) and an account from the seed script. Sharing, snapshots and email have optional variables, listed under [Environment](#environment). The other `.env.local` values are for the widget.

## Routes

| Route                   | What it is                                                                                                                                     |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `/login`                | Sign in with email and password. `?next=<path>` returns there afterwards.                                                                      |
| `/reset`, `/reset/[t]`  | Ask for a password reset email; choose a new password from its link. `noindex`, referrer only to this site.                                    |
| `/api/auth/*`           | `POST login`, `logout`, `reset` (request) and `reset/complete`.                                                                                |
| `/`                     | Overview: every top-level folder as a glass folder card holding its newest projects (subfolders' included). Old `?folder=<id>` links redirect. |
| `/f/[id]`               | Folder: breadcrumb, subfolders, status filter and project cards. Unknown ids get a way back to the Overview.                                   |
| `/p/[id]`               | Viewer: Browse or Comment mode (shortcut `C`), pins on the canvas, comments panel. `?page=<n>` opens a page.                                   |
| `/s/[token]`            | Shared review link for clients: view and add comments. No workspace links; `noindex`, no referrer.                                             |
| `/api/shares`           | Owner share API (owner key in `x-squint-owner-key`): create (signed-in only), push, pull, images, revoke.                                      |
| `/api/s/[token]`        | Client share API: read, images, the company's logo (`brand/logo?v=`), add a comment, share-scoped capture.                                     |
| `/sandbox`              | Static sample page to review in Squint. The widget e2e specs also run on it.                                                                   |
| `/api/frame-check?url=` | Reports whether a URL may be shown in an iframe here.                                                                                          |
| `/api/capture`          | `POST { url, width }`: full-page JPEG snapshot of a public website (page size in `x-capture-*` headers). Signed-in users only.                 |
| `/review-link`          | Shareable widget link on previews (or locally with `PINPOINT_ENABLE_REVIEW_LINK=1`).                                                           |
| `/api/pinpoint`         | pinpoint widget API.                                                                                                                           |

Open `http://localhost:3000/sandbox?review=<token>` to try the widget.

## How Squint works

- **Storage.** Signed-in pages read the workspace on the server (`lib/workspace/session-workspace.ts`): the layout checks the session and the membership (`requireMember`), then renders the dashboard or viewer with the workspace's data, which the browser keeps in one `useSyncExternalStore` store (`lib/store/store.ts`, backed by `lib/workspace-client`). Each change shows at once and is saved through the workspace API (`/api/w/<id>/…`) in the background, one request at a time, in order. If the server refuses one, the change is rolled back and a toast says why ("deleted in another tab" for a 404). The workspace is read again whenever the tab comes back into view, and right after another tab of the same browser saves something (`BroadcastChannel`); the last write wins. Images (uploads, snapshots, comment crops) upload straight to Vercel Blob with a client token for their fixed path, then the server records them (`blobs/token`, `blobs/commit`); without Vercel Blob (local and e2e), they go through the file's own route into Postgres. Images are read back through member-only routes by the same logical keys the browser uses (`page:<id>`, `snapshot:<id>`, `crop:<id>`). Uploads (PNG, JPG, WebP or GIF, up to 15 MB) are downscaled to a 2400px longest edge and re-encoded as WebP or JPEG first. A signed-in browser never writes `squint:v3`: what an earlier local-first build left there (`localStorage` and IndexedDB) is only read, for the one-shot import (`lib/store/local-store.ts`). On a signed-in page with such data, a dialog asks "Import N projects into {workspace}?" (`components/app-state/ImportLocalData.tsx`). Import sends folders, then projects in batches under the import route's 4 MB limit, uploads every file the server says it still lacks, and clears the browser's copy only once everything it holds is in the workspace (`lib/workspace-client/import-local.ts`); a failure keeps it and offers Retry, which picks up where it stopped. A project whose id another workspace has, or that an earlier import brought in and is now in the trash, is skipped by name and the browser keeps its copy. Review links made before signing in join the workspace and stop deleting themselves. **Not now** asks again after the next sign-in; **Discard local data** asks to confirm first; data that can't be read is never cleared on its own (it can be kept, downloaded or discarded). An account in no workspace (the admin) sees a "No workspace yet" page instead of the dashboard. A project whose folder was deleted while it was in the trash, then restored, is filed into the oldest folder (or a new "Restored projects" folder, with a fixed id, so tabs filing at once make one). Pages render from the workspace the server read, from the first paint: no skeleton while the browser connects. After the session ends, the page shows **Sign in again**; once signed in, the workspace shows again without a reload. The theme has its own key, `squint:theme`.
- **Pages.** In the New project dialog, Image takes one or more files (up to 50). With several, choose **One project per file** or **Combine into one project**; combined pages can be reordered by dragging their handles, or by focusing a handle and pressing the up and down arrow keys, and any file can be removed first. Each file is prepared on its own, with its progress or error shown. A project with several pages shows **Page n of N** with previous and next, and a thumbnail strip with each page's open comments. `[` and `]` change pages directly. PageDown and PageUp read on like a PDF reader: they scroll the canvas by about a screen first, and change pages only once it's at the bottom (or the top). None of these keys work while typing. The address keeps `?page=<n>`, so links open the same page, shared links too. The comments panel shows **All pages** (the default; each card says its page, and selecting it shows that page) or **This page**. An image project holds its pages in reading order (`source.kind` is `pages`). Each page has its own picture and size, and every comment that isn't on a snapshot names its page (`pageId`). Page ids are unique within their project only.
- **PDFs.** PDF mode takes one PDF up to 50 MB. Its first kilobyte must hold a PDF header (`%PDF-`) before pdf.js sees it. pdf.js (`pdfjs-dist`, loaded only when a PDF is chosen) renders the pages one at a time in a worker bundled with the app (no CDN), each to a picture at most 2400 px on its longest edge, stored like an uploaded image. Progress shows as "Rendering page 4 of 18", and **Stop rendering** stops it and ends the worker. A PDF with more than 50 pages offers **Use the first 50 pages** or **Choose another PDF**. A password-protected, damaged or empty PDF, or a page that fails to render, adds nothing and says why. pdf.js runs locked down: no XFA, and nothing fetched from anywhere but the app. Its standard fonts, CMaps, ICC profiles and WebAssembly image decoders (JPEG 2000, JBIG2, color management) are copied from `pdfjs-dist` into `public/pdfjs/<version>/` before `dev` and `build` (`scripts/copy-pdfjs-assets.mjs`; git-ignored, about 2.5 MB in 196 files, never its scripting sandbox) and served same-origin. Pages are painted to a canvas, so nothing in them is a link or a form (see [Known limits](#known-limits) for what else a rendered page loses). Unless you give it a name, the project is named after the file, and its pages are "Page 1", "Page 2" and so on.
- **Folders.** Folders nest to any depth. **New folder** in the sidebar makes a top-level folder, and **New folder inside** (in a folder's menu on its page, on its card and in the sidebar) makes one inside it. A folder's page shows where it sits (Overview › … › folder; deep paths fold their middle behind "…"), then its subfolders as folder cards, then its projects. A folder's count includes every project inside it at any depth; a folder with subfolders says so ("5 projects in all" on its card and in the sidebar). The sidebar shows the folders as a tree (`role="tree"`) with one Tab stop: the up and down arrow keys, Home and End move through it, right and left open and close a folder (or go to its first subfolder or its parent), and Enter opens its page. Shift+F10, or the context-menu key, opens the focused folder's menu, and Escape brings focus back to the folder. Open folders are remembered in this browser (`squint:folder-tree`), and the open folder's parents open to show it. **Move folder** (in each folder's menu) picks a new place in the folder tree, or the top level; a folder can't go inside itself or its own subfolders (those choices are shown, disabled, with the reason), and **Move project** picks from the same tree. Each folder records its parent (`parentId`, `null` at the top level). On load, a folder whose parent is missing moves to the top level, and folder cycles are broken.
- **Overview.** `/` and `/f/[id]` share one layout, so the sidebar stays put and its active indicator glides between Overview and folders. Each folder card is one link to its folder page: click or tap the glass, the artwork or the Squiggy key. Hovering a folder, or tabbing into it, fans out its four newest projects, and each one links to the viewer. The `···` chip in the card's top-right corner makes a new folder inside it, renames it, moves it or deletes it. A project created on the Overview drops into its folder and you stay put; the toast offers **Open**. Each folder gets one Native Pet product color from its place in the grid (`lib/brand-palette.ts`), shared by its generated artwork and its mascot, so no two folders in a row or column match. A folder's color can change when the column count changes or folders are added or removed; its art style and arrangement come from its id and stay the same.
- **Search.** The search field on the Overview and folder pages (top right on wide screens, in the sidebar's header on narrower ones) finds any project or folder by part of its name, in any folder at any depth, ignoring case and accents (`lib/store/search.ts`). Results are grouped into Folders and Projects (names that start with the query first, then A to Z; up to 5 folders and 8 projects, with a count of the rest), and each shows where it sits ("Client work › Q4"). The up and down arrow keys move through them, Enter opens one, ⌘Enter (Ctrl+Enter) opens it in a new tab, and Escape clears the field, then leaves it. `/` or ⌘K (Ctrl+K) focuses it from the Overview or any folder page, except while typing or with a dialog open. On phones it's an icon button that opens the field across the header.
- **Undo.** Deleting a project or a comment, and resolving a comment, shows a toast with **Undo**. Deleting a project moves it to the workspace's trash, which is what Undo brings it back from. Deleting a folder deletes everything inside it, subfolders included (its projects go to the trash), and can't be undone. Its confirm counts the subfolders, projects, comments and share links that go with it. When any comments or share links would go, the folder's name has to be typed first ("Type Alpha to confirm"), and **Delete folder** or Enter before it matches explains what's missing instead of deleting. Otherwise Cancel is focused first. If the deleted folder's page, or a subfolder's, is open, Squint goes back to the Overview.
- **Status.** Derived, never stored: no comments is _Ready to review_, any active comment is _Comments in_, and all comments resolved is _Comments resolved_.
- **Frame check.** Before a website loads, `/api/frame-check` fetches it server-side (HEAD, then GET when needed; 6s timeout; up to 4 redirects) and reads `X-Frame-Options` and CSP `frame-ancestors`. Only `http` and `https` are fetched. Every hop is resolved first, and the server won't fetch an address that points at a loopback, private, link-local or otherwise non-public network.
- **Screenshot fallback.** Sites that refuse framing, can't be reached, or don't load within 15 seconds get a fallback with **Upload a screenshot instead** (the project becomes an image and keeps the original URL) and **Open site in new tab**. When the server can't tell (for example a local address), the browser simply tries.
- **Snapshots.** On a website project, Browse shows the live iframe and Comment mode shows a full-page snapshot, taken server-side at the stage's width (`lib/capture`). Pins are placed on the snapshot, so they scroll with its content. **Refresh snapshot** takes a new one, and earlier comments stay on the snapshot they were placed on: their card says _Earlier snapshot_, and selecting one switches the stage to it. If the first capture fails, the stage says why and offers **Retry**; owners can also upload a screenshot instead. Snapshot and screenshot images are workspace files, and earlier snapshots are kept, so an Undo always finds what it brings back.
- **Capture safety.** `/api/capture` accepts only `http` and `https` addresses and checks the address the same way the frame check does. Every connection the headless page makes, redirects and subresources included, goes through a per-capture proxy that refuses non-public addresses when it connects. Limits: width 320 to 2560 px, height 16,000 px (taller pages are cut off), image 4 MB (a bigger page is rendered at a smaller scale, which is recorded on the snapshot), 25 seconds per capture, two captures at a time per server instance (on Vercel the second waits for the first), and ten requests per minute per IP. Locally it uses the Playwright Chromium from `pnpm exec playwright install chromium`; on Vercel, `@sparticuz/chromium-min`, which downloads the Chromium pack for the function's architecture on first use and keeps it in `/tmp`. With `SQUINT_CAPTURE_URL` set, captures go to an external service with the same contract instead (see [Environment](#environment)).
- **Comment screenshots.** Posting a comment saves a JPEG of the part of the snapshot or image that was on screen, with the pin marked. It shows on the comment card and opens larger.
- **Export.** The viewer's **Export** menu downloads a ZIP, or the Markdown or JSON on its own (`lib/export`). The ZIP holds `comments.md`, `comments.json` and `screenshots/<NN>-<id>.<ext>` (`<NN>-p<PP>-<id>.<ext>` for a pin on page `<PP>`; `.jpg`, or `.png` for screenshots saved before they were JPEG), plus a page project's page images in `pages/<PP>.<ext>` and the full-page snapshots the comments sit on in `snapshots/`. Images are capped at 40 MB in total: pages with comments first, then the other pages, then snapshots; the rest are listed as left out. The Markdown is written for AI coding agents: a short header on how to use it (with a page project's pages listed), then one section per comment, active ones first, each saying which page it's on and where in page px. The JSON follows the versioned schema `squint.comments/2`; what changed from `squint.comments/1` is noted in `lib/export/json.ts`. Files are named `<project-slug>-comments-<yyyy-mm-dd>.<ext>`. Export is disabled, with the reason shown, until the project has a comment.
- **Sharing.** **Share** in the viewer creates a share link (`/s/<token>`) to one project and uploads a copy of it to the share. Only signed-in users can create links (`POST /api/shares` answers 401 otherwise); the link is then attached to the workspace project (`share-link`), so any of the workspace's browsers can copy it and sync it, and client comments pulled from it are saved to the workspace as guests' comments, with no author account (`fromShare`, accepted only for a comment a guest posted on that project's link).
  - **Brand.** A workspace's link shows its company: the name and logo in the top bar and in How it works, and the brand color as an accent only (the top bar's rule and the logo's frame, never behind text). Squiggy stays Squint's. The client view carries `brand: { custom, name, color, hasLogo, logoVersion }` and nothing else of the workspace: no ids, keys or paths. The logo is a `workspace_blobs` row with no project at `ws/<workspaceId>/brand/logo/<id>`, named by `workspaces.logo_blob_key`; guests read it through `/api/s/<token>/brand/logo?v=<logoVersion>` (a one-way hash of its key), kept privately for 5 minutes at the current version and never by a shared cache, typed from its bytes, and 404 like an unknown link without one. Anonymous links keep Squint's own name and look (`lib/share/brand.ts`).
  - **Link previews.** A workspace's link unfurls as "{Company} invited you to review {Project}", with its own card (`/s/<token>/opengraph-image` and `twitter-image`): the company's logo when it's a PNG, JPEG or GIF (the card renderer can't draw WebP; then the name stands alone), its name, and the project's name. Cards are cached privately for 5 minutes, so a rename or revoke shows on the next unfurl. Anonymous links, and links that don't open, keep the generic card (`/s/opengraph-image`).
  - **Clients** see every pin and comment, can browse, take snapshots of the project's own address (never an address they choose), and add comments with screenshots. They can't resolve, edit, delete or move anything. They can export what they see (ZIP, Markdown, JSON). The page has no links into a workspace, is `noindex`, and sends no referrer.
  - **Sync.** The owner's viewer pushes every change to the server and pulls client comments on open, every 15 seconds while the tab is visible, and on focus. The owner's copy wins. The client's view refreshes on the same schedule.
  - **Revoke.** **Revoke link** revokes it through the workspace, deletes the server copy, and the link answers 404. Sharing again creates a new link. Deleting a shared project, or a folder holding shared projects, moves the project to the trash: its link answers 404 at once, and works again if Undo restores it. The daily cleanup deletes it with the project.
  - **Pages.** A page project's pages travel with it, each picture under its own key (`page:<pageId>`, then `page:<pageId>:<rev>` once its picture is replaced, so a replaced page is uploaded again). A client's comment names the page it's on, and the server refuses a page the project doesn't have. Before anything is uploaded, the share dialog checks the project's images against the limits below and says when the project is too big to share. Shares created before pages are converted by migration `006_squint_share_pages`, with the same page id the owner's browser gives the project, so nothing is sent again.
  - **Unsent comments.** A comment that fails to post keeps the composer open with its text, an inline error and **Retry**, and its pin is marked unsent. Sending again reuses the comment's id, so it can't post twice.
  - **Security.** The share token and the owner key are 32 random bytes each; the server stores only their SHA-256 hashes and compares them in constant time. The owner key travels in `x-squint-owner-key`. The server enforces who can do what; the UI only reflects it. Client writes are rate limited per IP: 20 comments and 6 captures a minute.
  - **Storage.** Shares live in Postgres when `DATABASE_URL` is set. Without it, they live in the server's memory, one copy per instance, lost on restart. That is for local use only: on a Vercel production or preview deployment without `DATABASE_URL`, creating a link answers 503 `storage-unavailable` and the Share dialog says so. Images go to Vercel Blob (private) when `BLOB_READ_WRITE_TOKEN` is set, otherwise into the share store, and are only served through token-gated routes (`lib/share`, `lib/share-client`). No request or response carries more than 4 MB of image, since Vercel Functions stop at 4.5 MB: bigger images upload in parts and download in byte ranges.
- **Pin anchoring.** Pins are stored as percentages of their surface: a snapshot, or a page. Website comments from before snapshots are anchored to the visible frame instead, shown only in Browse mode and labelled _Live page_.

## Accounts

There is no public signup. `pnpm --filter @pinpoint/demo seed:accounts` creates the admin, the company workspace and its owner from the seed variables ([Environment](#environment)), after running migrations. It reads the process environment only, is idempotent (a second run changes nothing and never overwrites a password), and prints emails and outcomes, never passwords. Roles: `admin` (and, from Milestone 4, `/admin`) and `company`, the owner of one workspace.

- **Signing in.** `/login` takes email and password. Passwords are hashed with Argon2id (19 MiB, 2 passes, 1 lane; `@node-rs/argon2`). A wrong password and an unknown email take the same time and get the same answer, "Invalid email or password. Check both and try again, or reset your password.", where "reset your password" links to `/reset`.
- **Rate limit.** 5 failed sign-ins per email, or 20 per IP address, in 15 minutes lock further tries (even with the right password) with 429 and `Retry-After`, and the form says how many minutes are left. Attempts are kept in Postgres (`login_attempts`), so the limit holds across serverless instances, and each one is claimed before its password is checked: in one transaction, under advisory locks on the email and then the address, the window is counted (attempts still being checked included) and the attempt recorded or refused. So the limits hold however many requests arrive at once. A wrong password leaves its row as a failure; a success deletes it and that email's earlier failures.
- **Sessions.** The `squint_session` cookie holds 32 random bytes; Postgres keeps only their SHA-256 (`sessions`). The cookie is httpOnly, SameSite=Lax, and Secure everywhere except plain http on localhost. A session lasts 30 days from its last use. **Sign out** (at the foot of the sidebar) deletes it. Resetting a password ends every session of that account, and `rotateSessions` does the same for a password change (Milestone 2's UI).
- **Password reset.** `/reset` always answers the same, whether or not the email has an account. Links are single-use, last one hour, are stored hashed, are capped at 3 per account per hour, and point at `AUTH_URL` (else the site's URL), never the request's host. Emails go through Resend; without `RESEND_API_KEY` the server logs "reset email skipped" instead.
- **Who sees what.** `middleware.ts` sends browsers without a session cookie to `/login?next=…` (API routes get a 401). Public: `/login`, `/reset`, shared links (`/s/*`, `/api/s/*`, `/api/shares/*`), `/px/s/*`, `/embed/*`, link preview images, `/sandbox`, `/review-link`, `/api/pinpoint`, `/api/frame-check` (the shared viewer uses it), `/api/cron/*`, `/api/auth/*`, `/pdfjs/*` and static files (`lib/auth/public-paths.ts`). The cookie's presence is all middleware checks: pages check the session itself (`requireSession()` in the workspace and viewer layouts), `requireMember(workspaceId)` answers 404 to anyone outside a workspace, admins included, and `requireAdmin()` is for `/admin` only (`lib/auth/guards.ts`).
- **Auth routes** refuse posts whose `Origin` is another site (or `null`), and log storage errors by kind and code only. The reset pages send `Referrer-Policy: same-origin`, not `no-referrer`: the link's token still never leaves in a Referer, and their form posts keep a real `Origin`.
- **Before hydration.** The sign-in and reset forms have `method="post"` and an `action` pointing at their route, so a submit before the page hydrates posts the fields in the body, never in the address. The routes answer such form-encoded posts with a 303: on to `next` (signed in), `/reset?sent=1`, or `/login?reset=done`, or back to the form with an error code (`?error=invalid-credentials`, `?error=mismatch` and so on), never with anything typed. Once hydrated, the forms post JSON as before.
- **Schema.** Migrations 008 to 022 add users, workspaces, memberships (one owner per workspace), sessions, password resets, login attempts, the workspace content tables (folders, projects, pages, snapshots, comments), a Blob ledger with `storage_usage` kept by triggers, and an audit log. Migration 022 links shares to a workspace. The dashboard and viewer read and write them through the workspace API.

## Squiggy

Squiggy is Squint's mascot. Its accessible name is "Squiggy, " plus the mood's label from `moods.ts`, such as "Squiggy, thinking"; Idle reads "relaxed" and Resolved reads "celebrating". The mascot component is `Squiggy` (`components/brand/mascot/Squiggy.tsx`).

The Squiggy at the top of the Overview reacts to the workspace (`lib/squiggy`). Its mood comes from four layers, highest first (a reaction lasts 2.4 seconds):

| Layer     | When                                                                       | Mood                           |
| --------- | -------------------------------------------------------------------------- | ------------------------------ |
| Reaction  | Signing in (the first page after `/login`)                                 | Happy                          |
|           | A comment is resolved                                                      | Resolved                       |
|           | A project is created                                                       | Happy                          |
|           | A project, folder or comment is deleted, or a change can't be saved        | Surprised                      |
| Attention | Squiggy is poked (for 1.6 seconds)                                         | Happy, with a wink             |
|           | A New project button is hovered or keyboard-focused, or its dialog is open | Listening                      |
| Asleep    | No pointer, keyboard, touch or wheel input for 60 seconds                  | Sleeping, until the next input |
| Ambient   | No projects (until the first input of the visit)                           | Sleeping, then Idle            |
|           | 10 or more active comments                                                 | Surprised                      |
|           | Any active comments                                                        | Thinking                       |
|           | Every comment resolved                                                     | Happy                          |
|           | Only projects without comments                                             | Idle                           |

The latest reaction replaces the one showing; there is no queue. Undo never triggers one. Listening starts once a New project control has held attention for 150 ms and lasts 400 ms after it lets go, so a passing pointer doesn't count and moving between controls doesn't flicker. An ambient mood stays at least 1.5 seconds before the next replaces it. The thresholds and timings are constants in `lib/squiggy/mood-engine.ts`. The store's actions (`lib/store/actions.ts`) emit the events (`lib/squiggy/events.ts`), so every way of resolving, creating or deleting is covered.

When Squiggy has something specific to say, its line replaces the hero's subline: "3 comments waiting in Client work" (a link to the folder with the most active comments directly inside it), with "(12 across all folders)" added when other folders have active comments too, or "All caught up. Every comment is resolved." With no projects, or only projects without comments, the usual subline shows. During a reaction, the bubble shows a line for the event instead, never a link: "Hi there. Glad you're here." (a first sign-in) or "Welcome back." (a return; `/login` sends the browser on with `?welcome=first` or `?welcome=back`, and the flag is removed from the address once Squiggy has seen it), "All moved in." (an import of local data, once its summary closes; "Most of it moved in. A few items need another look." when some items stayed behind), "One down. Nice." (resolved), "Homepage is in and ready to review." (created; a name over 32 characters is cut after its last whole word that fits, with "…"), "Gone. You can still undo it." (a project or comment deleted, while its toast offers **Undo**; a deleted folder, which has no Undo, gets "Gone. That one can't be undone."), or "That didn't save. Check your connection and try again." It lasts only what's left of the reaction's 2.4 seconds, also when Squiggy appears after the event (a resolve, then straight back to the Overview), and then the bubble goes back to the workspace line or the subline. The bubble never changes the hero's height: an invisible copy of the usual subline sizes it. Every line is plain text, not announced; the toasts already announce each event. With reduced motion, the moods still change, as still poses.

Every other Squiggy (the comment panel's tabs, folder keys, empty states and error pages) keeps its own fixed or contextual mood. On the sign-in and password pages, while any password field shows its password, Squiggy shuts its eyes and looks aside; the body keeps the form's mood, and the accessible name doesn't change. Its root carries `data-mood` and `data-eyes` (`mood`, `averted` or `held`).

## Data retention

Shared copies of projects made without signing in are deleted 30 days after they were created (`lib/share/retention.ts`). Workspace projects aren't: shares linked to a workspace (`workspace_id`, migration 022) have no deletion date and are never expired by the cleanup, and only the workspace's trash is emptied after 30 days.

- **Notice.** From 5 days before, a shared link's page shows a "Deletes on Nov 3" notice. In the last 24 hours it counts down like the review window.
- **Minimum notice.** Nothing is deleted before its notice has shown for 5 days. A share is deleted 30 days after its project was created, or 5 days after its link was created if that's later. Shares that existed before migration 007 also get at least 5 days from when that migration runs, even if they were already past 30 days.
- **Shared links.** An expired link stops working right away and answers 404, even before the cleanup deletes it.
- **Rolling deploys.** Every deployment since migration 007 sends `expires_at`; migration 022 dropped its default, and a CHECK still requires it on anonymous shares.
- **Workspace trash.** Deleting a workspace project moves it to the trash (`projects.deleted_at`, migration 024): it leaves every list and its share answers 404 until it's restored. The daily cleanup deletes it for good 30 days later, with its share, pages, snapshots, comments and files; a project restored before then is never touched. A folder can be deleted once no live project is left in it; trashed projects inside move to the workspace root (migration 026), still restorable, and come back there.
- **Daily cleanup.** Vercel Cron calls `GET /api/cron/expire` once a day (`vercel.json`). It deletes expired shares, deletes Blob files a failed delete left behind once they're 31 days old, deletes workspace projects 30 days in the trash, deletes workspace files whose project is gone and uploads never committed (a day old), and deletes pinpoint pins 30 days old in Postgres or GitHub storage (pins get no notice). Each step runs on its own, so one failing doesn't stop the others. When a run hits its time limit, the next one carries on.
- **`CRON_SECRET`.** The route only runs with `Authorization: Bearer $CRON_SECRET`, which Vercel Cron sends. Without `CRON_SECRET` it answers 503 and nothing expires; with a missing or wrong header it answers 401.
- **Previews.** Vercel Cron only runs on production deployments. To run the cleanup on a preview, call it yourself:

  ```sh
  curl -H "Authorization: Bearer $CRON_SECRET" https://<preview-url>/api/cron/expire
  ```

- **Response.** One result per step:

  ```json
  {
    "shares": 2,
    "blobs": 0,
    "trash": 1,
    "workspaceBlobs": 3,
    "pins": null,
    "done": true,
    "failed": {
      "shares": false,
      "blobs": false,
      "trash": false,
      "workspaceBlobs": false,
      "pins": false
    }
  }
  ```

  Each count is how many it deleted, or `null` when the step was skipped (no Blob store or database, or pin storage that can't expire) or failed. `done` is false when time ran out or a step failed. Any failed step makes the response a 500.

## Known limits

- **Signed-out captures.** Snapshots are taken server-side, so pages behind a login are captured signed out, and personalized or location-dependent content may differ from what a reviewer sees.
- **Snapshot size.** Captures are scaled down as needed to stay under 4 MB, so a long or detailed page can come out at a lower resolution. Pages taller than 16,000 px are cut off.
- **Per-instance limits.** Rate limits (except sign-in's, which is in Postgres), the reset request's per-IP brake and the two-captures-at-a-time cap are kept in memory, so they apply per server instance, not across a deployment.
- **Untested backends.** Postgres runs in the unit tests on PGlite (Postgres compiled to WebAssembly) and in the e2e suite on a local Postgres 17, not yet on a hosted one. Vercel Blob storage hasn't been tested against a live store.
- **Capture endpoint.** `/api/capture` needs a valid session: it checks the session itself, not just that the cookie is there, and answers 401 `{ "error": "unauthenticated" }` otherwise. Guests capture through their share's own route (`/api/s/[token]/capture`), which only ever snapshots the shared project's address.
- **Cold starts.** On Vercel, the first capture on a new instance is slower while Chromium starts.
- **Share size.** A share holds up to 40 MB of images: 2 MB per comment screenshot, 8 MB per snapshot and 15 MB per page. A project's pages are stored to fit in 32 MB of that, so any project of up to 50 pages can be shared with room for snapshots and screenshots: each page gets up to 1.2 MB, and in a project of more than 27 pages an even share of 32 MB (about 670 KB at 50 pages). Combined images over their share are re-encoded when the project is made, and PDF pages are rendered to fit. If snapshots and screenshots take a project over 40 MB, the share dialog says so before anything is uploaded.
- **PDF fidelity.** Each PDF page becomes a flat picture, at most 2400 px on its longest edge and re-encoded as WebP or JPEG at 1.2 MB or less (less in PDFs of more than 27 pages; see Share size). A page that doesn't fit at full size is drawn smaller, down to 1000 px on its longest edge, so very fine print can come out soft, and a page too detailed to fit even then stops the import ("Page 4 of that PDF is too detailed to store"). Text can't be selected or searched, and links, form fields, media and scripts don't work. XFA forms aren't rendered, so such a PDF shows only its regular page content, which for some forms is just a placeholder.

## Tests

`pnpm test:e2e` from the repository root (run `pnpm exec playwright install chromium` here first), with `E2E_DATABASE_URL` set to a throwaway Postgres on `127.0.0.1` or `localhost`; the suite refuses to start otherwise, because its setup empties every table there. For example:

```sh
docker run -d --name squint-pg -e POSTGRES_USER=squint -e POSTGRES_PASSWORD=squint \
  -e POSTGRES_DB=squint_e2e -p 127.0.0.1:54329:5432 postgres:17
E2E_DATABASE_URL=postgres://squint:squint@127.0.0.1:54329/squint_e2e pnpm test:e2e
```

The global setup empties that database and runs the seed script against it; a `setup` project then signs in once through `/login` and saves the session cookie (`e2e/.auth/`, git-ignored), which every other project starts from. Each test starts from an empty workspace (`e2e/test.ts` empties its content tables first, `e2e/workspace-db.ts`), and specs that need data put it in through the server's import route (`seedWorkspace`), never into `localStorage` (except `e2e/import.spec.ts`, which seeds it to test the import). `e2e/login.spec.ts` covers signing in and out, the rate limit and password reset. The server gets `DATABASE_URL=$E2E_DATABASE_URL` through its environment (which wins over `.env.local`), blank Blob, Resend and `AUTH_URL` variables, so a run never reaches real services (workspace files go into the e2e Postgres), and a test-only `AUTH_SECRET` to seal review links. The suite builds into `.next-e2e` and runs on desktop Chrome and a Pixel 7 profile. Squint specs mock `/api/frame-check` and `/api/capture`, so they never touch the network. `pnpm test` runs the unit tests (Vitest). Postgres runs in them as PGlite, which handles one transaction at a time; to check the login limits under real parallel requests too, set `TEST_DATABASE_URL` to a throwaway local Postgres (`127.0.0.1` or `localhost`, e.g. a `squint_unit` database in the container above). Without it, `lib/auth/login-concurrency.test.ts` is skipped.
